# XuanShu 业务本质、竞品公开对标与全栈差距审计

**审计日：2026-10-10。项目仍为 `v.0.1.0`（未发布），不建立版本分支。**

> 这是一份根据第三方公开产品描述、玄枢实际代码和当前自动化测试形成的**产品与技术审计**。第三方宣传不是可重复的能力实测；本项目不得抓取其私有接口、提示词、受限源码或付费数据。传统术数仅作为文化解释框架，不是可证明的个体命运、健康、投资或关系预测模型。

## 1. 业务定义：从“报表生产”转向“问题驱动的多体系咨询”

用户不是为了获取一串干支或十二宫 JSON，而是带着具体问题而来：职业转型、发展节奏、恋爱和沟通、合作关系、搬迁择时、人生阶段复盘。产品应该完成以下循环：

`真实问题 → 资料/出生时间校验 → 咨询路线规划 → 计算工具调用 → 传统规则检索 → 跨体系一致性与差异核对 → 同现实事实分层分析 → 人可理解的咨询报告 → 追问/修正 → 有明确同意的长期事件记录 → 后续复盘`。

**对 ChatGPT/Claude 的技术定位**：玄枢提供模型无关的、确定性的专业计算与规则证据能力；LLM Host 提供语言理解、交互和组织能力。既可通过 Agent Skill 协调工具，也可将来提供独立多模型 Agent Runtime。**MCP/Skill 是交付协议，不是主营业务本身。**

目标输出的五层：①出生输入和流派/时制说明；②精确计算字段；③传统符号意义与出处；④用户明确给出的现实情境和可供比较的行动选项；⑤不确定性、反证及下一轮追问。没有足够数据时停止而不是虚构。

## 4. 最需要补齐的八大业务能力

### A. 真正的咨询 Agent（最优先）

- 独立 Coordinator：读懂用户**问题与现实背景**，选择 `natal / annual / relationship / timing / scenario / verification` 路径；仅询问缺失且必要的信息。
- Tool Planner：命盘先校验时区/出生误差，按需调用八字/紫微/奇门；**不应每个问题强制调用所有术数**，避免伪多 Agent。
- Evidence Verifier：任何具体星曜、宫位、四化、日柱、节令都必须来自工具结果；强制字段路径与方法版本；检查前后结论的矛盾。
- School Arbiter：把“口径差异”与“算法错误”分开。来自同一出生资料、同一历法依赖的多个体系不算独立统计验证；严禁将一致性换算为成功概率。
- Report Composer：按关注问题输出用户可读的核心观察、传统规则解释、现实约束、替代方案、未知项与可追问点。
- Conversation State：多轮连续继承已确认的出生资料、流派、时区和研究范围；明确区分当前对话临时状态与需要同意才能保存的长期记忆。

执行位置可以是 ChatGPT/Claude 调用本项目 `structured-dossier` Agent Skill + MCP，或者本项目后续的多模型 Agent Runtime。**当前只具备工具和可移植的规划说明，并未运行自主 LLM Agent。**

### B. 专业领域深度（不是堆星曜数量）

1. 紫微：建立可选流派配置（全书、钦天、北派等，只有证据充分的才发布），把安星、四化、宫干飞化、流曜和运限拆为版本化规则模块。优先用开源真实运行全盘逐宫验算，至少覆盖不同性别、闰月、交节、子时、生年干与十年宫限切换。未知流派输出“未支持”，不要无声回退。
2. 八字：完整命式字段与大运交运分别验盘。喜用神、旺衰、格局等存在理论分歧，必须具独立规则文献、适用条件、反例和方法 ID 后才允许解读，不得由 LLM 直接臆断。
3. 奇门：把时家拆补的可验参考盘加到完整九宫逐字段；其他起局方式独立配置，不把“一个流派”冒充全部。选择日期需扫描多个候选时间并输出边界、时区、方法选择与现实限制。

### C. 规则知识库

每一规则的最低记录为 `rule_id / school / edition / source_title / source_locator / kind / premises / computation / exceptions / conflicting_rules / test_fixtures / reviewer / validation_status / last_checked`。知识库应优先检索已审校的结构化规则，然后检索可合法使用的原典引文；AI 不能把网络摘要、模型生成解释和古籍原文混为一谈。严格区分**方法出处**与**对具体命盘的验盘证据**。

### D. 人生经历与长记忆

长期记忆至少分四类：`confirmed_birth_profile`（本人提供）、`confirmed_events`（用户确认过的经历）、`user_preferences`（咨询目标）、`previous_findings`（带来源与状态的历史结论）。系统应支持用户逐条查看、纠正、删除、导出，并限定事件关联的用途。未经用户同意不保存出生资料、亲属资料或情感经历。人生事件是**回顾性记录**，不宜宣传成经科学验证的命运概率校准。

### E. Life Path 多情景分析

对比继续现职 / 转职 / 创业等方案时，采用“传统标签时间轴 + 用户提供的现实条件 + 显式主观偏好 + 最坏/最好/基准情境”四层，不制造虚构的未来分支、确切时间或百分比。需要可编辑的假设、因果标记（事实/推测/传统）以及更新情境后重新推演。

### F. 关系与择时咨询

合盘：先确认双方是否同意提供信息，再做双方盘 + 传统结构比较 + 双方现实沟通目标的分层说明。择日：允许输入多个候选时刻，分别精确排盘，再叠加用户的实际可行性约束；禁止没有根据的“一定吉利”或“必然幸福”。

### G. 产品体验

入口需要从“21 个工具标签页”转向一个**以问题为中心的对话台**：资料确认卡→可视化工具时间线→焦点命盘→传统解释与证据定位→现实选项→保存/撤销。专家仍保留盘图和高级参数，普通用户无需知道 MCP/CLI/具体神煞名字。ChatGPT/Claude 版本应直接依靠 Agent Skill 对话，而不是强迫用户手动选择 24 个工具。

### H. 可靠交付

线上关键验收不看源码 ZIP 是否存在，而看真实 `ChatGPT → HTTPS → OAuth → MCP tools/call → 计算结果 → 解释 → 后续追问`，Claude 亦独立跑一遍；另验租户隔离、Token audience/scope、断线重试、速率限制、日志脱敏及删除请求。私人 Skills-only 插件不是此链路的替代品。

## 5. 推荐的架构：模型无关的业务中台

```text
                  ChatGPT / Claude / Codex / XuanShu Web
                              │
                     Consultation Coordinator
            ┌─────────────────┼───────────────────┐
     Session context     Consent-gated memory   Plan/Tool Router
            └─────────────────┼───────────────────┘
                              │
                        Evidence Pipeline
           ┌──────────────────┼───────────────────┐
    BaZi/ZiWei/Qimen     Rules/School Registry   Reality References
    deterministic core  versioned provenance    user-confirmed/current
           └──────────────────┼───────────────────┘
                              │
                 Conflict & Safety Validator
                              │
               Consultation Report / Next Turn
                              │
                       MCP / REST / CLI
```

设计规则：
- 计算引擎只输出可重复的结构事实，不能让 LLM 重算天文时刻或安星表。
- Agent 推理输出可以变化，必须以计算引用、流派限定、外部事实来源锁定，保留工具执行轨迹（不输出模型私有思考内容）。
- Memory 是**可选且需要同意**的业务能力，不能默认把 ChatGPT/Claude 账户、用户出生资料与服务器持久账户视作已经连通。
- 故障降级应显式：专业紫微依赖不可用时报告不可用，而不是默默替换成部分原生盘。

## 6. 投入优先级（按照用户真实价值，而非代码容易程度）

| 顺序 | 工作包 | 为什么现在要做 | 完成条件 |
|---|---|---|---|
| **P0-1** | Consultation Coordinator / 总控 Skill / 问题路由 | 打通真正的主营业务 | 至少六类用户问题能够自动制定工具链，保留焦点、来源和前后轮次约束；不伪称内置 LLM |
| **P0-2** | 紫微专业动态盘 + 八字/奇门黄金盘集 | 保证深度解释有正确输入 | 外部独立逐字段对照（主辅星、运限、四化/整盘九宫），差异可归流派、时区或错误；缺字段=未验收 |
| **P0-3** | 规则知识库 / 版本化流派 | 防止“话术很深但无依据” | 报告里的每个技术术语都能追到规则 ID 和前置计算证据 |
| **P0-4** | 真正远程 MCP + 身份验证 | 实现你最初的 Plugin 目标 | ChatGPT、Claude 各跑完整授权和真实调用；退出、撤销和越权测试通过 |
| **P1-1** | 多轮会话+授权记忆+人生事件时间轴 | 将一次性算命工具变成持续咨询服务 | 同用户追问复用参数、可修改/删除/导出，跨用户数据不能访问 |
| **P1-2** | Life Path 情景推演及现实资料层 | 覆盖择业/迁移/重大抉择 | 传统标签与现实依据明确分开，方案输入和假设可反复调整 |
| **P1-3** | 双人深度合盘与多候选择时 | 补齐官方面向用户的典型高价值业务 | 在同一会话中处理两个资料、多个时间窗口，不遗漏授权或时区 |
| **P2** | 界面重构、模型适配、审计观测、商用运营 | 具备扩展和运营能力 | 网络端到端测试、可访问性、性能基线、运营可观测和安全审核 |

**P0 工作包可以并行开发，不代表 P1/P2 可忽略或永久搁置。** 先保证可追溯的完整咨询路径，再扩大命理规则，最后大规模增加工具数量；由用户场景驱动是否需要新工具。

## 7. 验收指标——不得与“科学预测准确率”混淆

- **咨询任务通过率**：六类代表任务（出生结构说明、某一年职业反思、双人关系、候选择时、决策分支、跨轮修改）的全链路可重复成功率；初期目标 6/6。
- **工具事实可信度**：测试集中的星曜/四柱/节气**零编造**，引用字段存在率目标 100%；计算准确性另做异源黄金盘比对，不能由该指标替代。
- **源证分离**：每一条判断标记 `computed / traditional / factual / user-provided / hypothesis`；缺乏证据的内容标为未知，不做概率伪量化。
- **条件连续性**：改年份只更新年份、改流派则比较两套方法，后续追问不得丢失已确认的时制参数。
- **隐私**：用户未同意不得服务器存储；记忆可浏览、可删除、可撤销；二人资料需独立确认用途。
- **外部交付**：生产服务的 ChatGPT 和 Claude 均完成真实 MCP 授权+工具调用+失败路径，不能用 mock 或 ZIP 存在代替。

## 8. 直接的产品判断

**玄枢已经有足够的“计算地基”，却缺“专业咨询中枢”。** 最重要的投入不是把 24 个 Tool 变成 250 个，而是让一段真实的人生问题自动完成「资料核查、领域路由、可信计算、跨体系解释、现实选项与追问」；并让这个过程能在 ChatGPT/Claude 原生客户端真正执行。

本轮对应的首个工程改动：强化现有 `skills/structured-dossier/SKILL.md` 和 MCP `prepare-report` 提示，把问题驱动、工具规划和证据层级规范落实为可移植指令，**仍不能宣称这等于一个已上线的自主 LLM Agent**。
